D365 Agent Blueprint

One architecture and one way of working for building AI agents across Finance & Supply Chain, Business Central, Sales, Customer Service and any Dataverse solution. Based on the patterns in Microsoft's FastTrack AI ERP agent templates.

Every D365 agent is a brain that is woken up by a trigger, looks things up and acts through tools, remembers its work in Dataverse, and asks a person before doing anything risky.

The golden path

All the FastTrack agents follow this sequence. The Sales Order Agent is a good example: an email with a PDF becomes a sales order in D365.

  1. Event arrivesEmail, D365 event, status change or schedule
  2. Register work itemOne Dataverse row with status New
  3. Gather & validateRead D365 master data, extract documents
  4. DecideApply policy, recommend with reasons
  5. Approve or reviewA person signs off on exceptions or risky actions
  6. Act & verifyWrite to D365, then re-read to confirm
  7. Log & notifyAudit row, email or Teams message

Why a work-item table with a status? A status change restarts the agent at the right step, a review app shows every item, and every decision leaves an audit row. This is the single most reusable idea in the FastTrack samples.

Worked example

Two sample agents

Credit Hold Review Agent reviews sales orders on credit hold in D365 Finance, adds customer context from Dataverse, recommends release or keep, and gets a credit manager's approval.

How it works

  • A simple automation checks the D365 hold list every 30 minutes in business hours and starts the agent only when there is a new hold.
  • One flow gathers credit limit, balance, overdue days and order amount, plus open opportunities and dispute cases from Dataverse. In Teams, people can also ask the agent about any hold.
  • An AI prompt applies the credit policy and gives 2–4 reasons that cite the numbers. Flow rules, not the model, decide when a person must review.
  • The credit manager approves in a Teams card. Every step is written to an audit table.

New→CaseReady→AwaitingApproval→Approved→Released→Closed

The same pattern (find exceptions, build the case, recommend, approve, act, log) fits invoice mismatches, requisition reviews, SLA escalations and blocked customers in Business Central.

Second example: Inventory Close Agent

For processes with many steps, the Period Close Agent pattern applies. This agent runs the month-end inventory close checklist in Supply Chain Management: open documents, negative inventory, production orders, journals, the inventory close itself, and the inventory-to-GL reconciliation.

  • Local behaviors hold the fixed mechanics: context, gates, status, audit, email. Developers own them.
  • Business skills hold the policy for each procedure. The cost controller edits them without republishing.
  • A task runs only when Agent enabled = Yes. Tags and names never authorize.
  • Two flows wrap every task: Start task checks, routes and claims it; Finish task records the result. The agent spends its effort only on the procedure itself.

Safety rules worth reusing

  • Exactly one live task per action, or stop
  • Status written only by audited flows and confirmed by a fresh read
  • Claims stop the agent being triggered twice by its own change
  • Cost accountant approves before the close starts, in batch
  • One email sender; recipients come only from Dataverse or D365

What else it can do

The same building blocks fit many other processes

If someone today notices something in Dynamics 365, looks up facts on several screens, judges them against a written rule, asks someone to approve, acts and tells others, an agent can do most of that work. The person keeps the decision.

Is your process a good fit?

  1. It happens often: weekly, or dozens of items a month.
  2. Someone looks things up on several screens today.
  3. There is a written rule, tolerance or approval limit.
  4. The data is reachable in Dynamics 365 or Dataverse.
  5. The result can be checked in D365 afterwards.
  6. A mistake can be undone, or a person approves first.
  7. You can measure the win in hours, days, errors or cash.

Better done another way

  • Moving data with no judgement: an integration or a simple automation
  • Answers in under a second, or thousands of items an hour: code or batch
  • Trends and analysis: reporting in Power BI
  • No agreed rule for what “right” looks like: fix the process first

Check Microsoft first. Microsoft ships its own agents in Finance, Supply Chain, Sales, Customer Service and Business Central. The best use cases extend them or fill the gaps between them. Every new agent starts by recommending, and earns the right to act once it has proved accurate.

Running cost

Two ways to build the same agent

Microsoft charges Copilot Studio by the step: about 5 credits each time the agent itself acts, and about 0.13 for each step inside an automated flow. So who does the routine work decides most of the Microsoft bill. Both designs make the same decisions, with the same approvals and audit trail.

Recommended

Lean: flows fetch, the agent judges

Automations find new work, read the data and record results. The AI steps in only to judge and explain.

Credit Hold, 300 holds a monthMicrosoft usage, rangeS$250S$190–440
Inventory Close, 16 tasks a monthMicrosoft usage, rangeS$118S$70–340

  • Same cost every item, easier to test
  • Rules run in flows the agent can't skip
Alternative

Flexible: the agent does it all

The agent checks for work itself and looks up each fact one by one, deciding what else to read.

Our default is Lean for processes that run every day at volume. We use Flexible for pilots, low volumes, or when you want the agent to investigate on its own, and you can switch an agent later without changing your subscription. Figures are Microsoft Copilot credits at about US$0.01 each, excluding your subscription, and are confirmed by measuring a validation run on your data before you commit.

Go-live gate

Is the agent production-ready?

  • Process owner and security have signed the design canvas
  • Every customer-specific value is an environment variable
  • Connections use least-privilege accounts through connection references
  • Every write to D365 is approved by a person or within a documented threshold
  • Every decision is logged in an audit table
  • Writes are verified by re-reading D365
  • Processing the same item twice cannot create duplicates
  • Evaluation set passed and stored with the solution
  • Data policy allows only the connectors the agent uses
  • Routine work runs in flows, not agent steps, and tools read only the fields they need
  • Copilot credits per item measured and billing configured
  • Runbook and owners documented
